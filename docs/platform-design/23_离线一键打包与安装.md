## 包结构

```text
harness-engineering-platform-<version>-<commit12>-<arch>/
  install.sh
  manifest.json
  program/                 # platform/、runtime/、plugins/、README/VERSION 等运行源码
    platform/plugin/node_modules/
    runtime/adapters/dsh-web/node_modules/
  offline/
    node/                  # 目标架构 Node 24 tarball
    pnpm/                  # 与锁文件一致的 pnpm
    python/                # 可选便携 Python 与 PyYAML wheel
    dsh/                   # DSH 离线安装树（构建后放入）
    git/                   # Git 客户端及依赖库/离线包（必带）
    docker/                # 可选发行版离线包
  images/
    dsh-<tag>.tar          # docker save 产物
  data/                    # 完整数据根快照，敏感
```

`manifest.json` 版本 1，记录包版本、Git 提交和 dirty、架构、源 `$HOME`/程序根/数据根、全部文件类型/权限/SHA-256、运行时组件版本、Git 来源、镜像 tag/Image ID/构建指纹/架构，以及敏感路径。包外生成 `.sha256`。

## Git 客户端

- 安装包必须包含 Git 客户端；不允许只依赖目标机系统 Git。
- 优先使用静态 Git 单文件；否则收集目标发行版的 Git 二进制、`/usr/lib/git-core`、`/usr/share/git-core` 和 `ldd` 依赖库，写成带 `LD_LIBRARY_PATH`/`GIT_EXEC_PATH` 的包装脚本。
- 安装器把 Git 放到 `<prefix>/runtime/git` 并前置 PATH；包内 Git 不可执行时回退系统 Git，并在回执和日志中说明回退，不静默写成已具备。
- 不为 Git 单独制作 Docker 镜像；Git 是宿主短命令，容器化会引入 cwd、uid/gid、凭据和包装成本。

## 打包

在线准备机先准备离线资源目录：

```text
assets/
  node/       # 目标架构 Node 24 tarball
  pnpm/       # pnpm 11.28.5
  git/        # 可选；不存在时从当前系统收集
  python/     # 可选
  dsh/        # DSH 构建产物，构建镜像后放入
  image/      # 镜像 tar（或使用 --image-tag 从 Docker 导出）
  program/platform/plugin/node_modules/        # 目标架构依赖
  program/runtime/adapters/dsh-web/node_modules/
```

生成安装包：

```bash
./platform/dsh-deploy pack \
  --out dist \
  --assets-dir <离线资源目录> \
  --data-root <完整数据根> \
  --image-archive <镜像 tar> \
  --allow-dirty
```

`--image-tag` 用于从本机 Docker 导出镜像；`--no-image`/`--no-data` 只用于测试或程序包场景。`--data-root` 必须是真实工作区；`--allow-fixture-data` 仅用于夹具测试，真实部署不得使用。打包器默认拒绝 dirty 工作树；`--allow-dirty` 会在 manifest 记录实际 dirty 状态。镜像构建、依赖安装和数据根一致性检查属于打包机操作，不进入目标机安装过程。

## 安装

```bash
tar xf harness-engineering-platform-<...>.tar.gz
cd harness-engineering-platform-<...>
./install.sh --prefix ~/work/harness-engineering-platform \
  --data-root ~/harness-engineering-platform-data --start
```

流程：校验 manifest、架构、全部文件 SHA-256 和目标目录；校验数据根是真实工作区（夹具默认拒绝）；恢复程序/数据根；按源 `$HOME` → 目标 `$HOME` 重写实例登记、Compose、`workspace.json`、`business-access.json` 等已知文件；安装 Node/pnpm/DSH/Git；`docker load` 并校验镜像；运行 `platform/dsh-platform prepare --offline`。`--dry-run` 只校验和展示计划；`--skip-image` 不导入镜像；`--strict-paths` 在仍有旧路径时失败。

不自动启动业务实例。安装回执列出待重建实例；旧平台 Session、网关 `host`/`publicOrigin` 和 Docker 命名卷不自动迁移。完整数据根包含平台密码和 LLM API Key，分发和存放必须按敏感制品管理。

## 本次误部署的根因与整改

- **直接原因**：207 打包和安装显式使用了 `hep-arm64-poc/fixture-data`；真实数据仓库在 228 未传入 207。当前旧安装包的 `source.dataRoot` 是夹具，`data/` 只有夹具的 `workspace.json` 和 `config/`，没有 `AGENTS.md`、`.agents/skills`、`agents/`、`evolution/`。
- **放大原因**：安装器允许任意 `--data-root`，没有校验真实工作区资产；安装完成也没有校验管理 Skill、数据工作区身份或默认工作区。验收只核对了 HTTP 登录/首页 200，按项目规则不足以证明部署完成。
- **平台行为**：管理助手的默认工作区来自 `HARNESS_ASSET_ROOT`；启动器把夹具路径写入 `hep-env.sh`，因此 `workspaceRegistry.initializeDefault` 初始化到夹具。平台 HOME 已有默认工作区时，单纯改环境变量不会自动切换。
- **整改**：部署真实数据仓库并改用真实 `HARNESS_ASSET_ROOT`；重建 Profile 使 `.agents/skills` 进入管理助手；创建新的平台 HOME，让默认工作区按真实数据根重新初始化；安装器新增真实工作区校验，默认拒绝夹具，仅测试可用 `--allow-fixture-data`；`prepare` 后校验 Profile 包含数据根 Skill 路径并写部署定位文件。
