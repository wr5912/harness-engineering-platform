# 23｜离线一键打包与安装

本文维护完整平台包与单智能体独立运行包的格式、来源、资源准备及安装用法。平台架构与实例编排原则仍由 [02｜系统架构与部署设计](02_系统架构与部署设计.md#packaging-deployment) 维护；实际验证状态以[项目验收矩阵](../ai-agent-harness项目验收矩阵.md)为准。

## 包类型与入口

| 任务 | 打包入口 | 目标机运行内容 |
|---|---|---|
| 部署工程平台与完整数据工作区 | `platform/dsh-deploy pack` | 平台管理界面、管理助手及所带工作区，由平台管理业务实例。 |
| 独立部署一个业务智能体版本 | 智能体详情的“更多操作 → 导出独立运行包”；CLI 为 `agent-preview`、`agent-prepare`、`agent-pack` | 所选业务 Harness 与标准 DSH Runtime，使用原生 DSH 对话界面。 |

以下两种包采用不同来源规则与安装器；完整平台包的 HEAD 快照、Git 恢复和平台网关配置不适用于单智能体包。

## 单智能体独立运行包

### 资产与运行边界

独立包要求同时指定 Agent ID 与 Experiment ID，并核对两者归属。依据该 Candidate 的 `harness.yaml` 装载声明收集 `dsh/workspace`、`dsh/presets`、`dsh/managed`；保存的是导出时实际已保存的文件字节，包括尚未提交 Git 的修改。manifest 记录所选身份、Candidate 摘要、来源提交、dirty、文件权限与 SHA-256。页面检查后若资产变化，正式导出会要求重新检查；复制期间再次核对摘要，不把不同时间的资产混为同一快照。

包内保留业务 Preset、提示词、Skill、本地知识、插件、代码变体和明确的运行依赖。固定编排按 Candidate 指定的不可变版本、所选 MCP 分组当前发布版本及其固定子版本收集连接闭包，不带其他编排的草稿和未使用历史版本。必要的业务实现作为运行制品装配；适配生成在 `runtime/`，冻结的原始资产保持不变。不会复制整个数据仓库、Git 历史、管理助手及其 Skill、其他 Agent、旧实例登记、原平台 HOME、Session、缓存或宿主 venv。

运行使用与目标架构匹配的当前标准 DSH 镜像；不为 Harness 或插件修改构建派生镜像。容器内有 Node、DSH 与所需原生运行环境，目标 Linux 主机无需安装 Node、Python、Git 或 DSH。目标机需要 Bash、常规解包与摘要工具以及可用的 Docker Engine/Compose；缺少 Docker/Compose 时，安装器调用包内离线引导，自动安装路径限于 root + systemd Linux。已有 Docker 的普通用户须具有访问 daemon 的权限。

安装后直接运行原生 DSH，不依赖原平台进程、管理助手、统一网关、平台风险评估或访问控制服务。包内普通 MCP 适配支持 MCP/OpenAPI、分组和已收集的固定业务编排；业务自身的 Guard、工具配置和 DSH 原生行为继续保留。外部推理模型、MCP 与业务接口仍须从目标环境可达，归档知识不能替代这些服务。

### 在线与离线知识

| 模式 | 已有本地资料 | 互联网参考资料 | 目标环境要求 |
|---|---|---|---|
| `online`（默认） | 随所选 Candidate 资产一起保留，包括其 Skill 和 LLM Wiki。 | 不额外下载；运行时仍可按原有能力访问在线参考。 | 实际使用的模型、MCP、业务接口和在线参考可达。 |
| `offline` | 同样保留。 | 静态扫描所选资产内文档和 Skill 的明确参考链接，优先使用已归档副本或页面指定的本地材料，其余在打包机取得快照。 | 模型、MCP 和业务接口须在目标网络内可达；已归档参考由离线读取提供方提供，不回公网补取。 |

离线参考输出到 `assets/workspace/knowledge/offline/`，包含来源索引、获取时间、原件或读取表示的摘要，PDF/DOCX 另有可读文本。该目录是打包制品，不直接编辑；知识正文仍在所属 Agent 的原资产中维护。页面可为参考链接选择当前 Candidate 中的 Markdown、文本、HTML、PDF 或 DOCX；新材料应先保存到所选版本，再重新检查。必需文档无法完整取得、本地引用缺失或越界时停止出包，并说明缺口。

检查会把服务地址、模型/二进制资源和用途不明的链接分别提示，不将它们当网页下载。静态扫描不能覆盖动态拼接地址、搜索结果或隐含背景知识，也不会自动下载 Hugging Face/ModelScope 权重、搭建任意推理环境。已保存到所选装载目录的权重文件按实际字节携带；包外模型目录、宿主挂载和动态加载路径不会自动收集，其加载路径、推理环境与目标算力仍需按实际 Agent 核验。离线完整性最终以目标环境的实际业务任务验证，不能由扫描通过推定。

### 页面导出与凭据

在智能体详情选择要导出的版本，打开“更多操作 → 导出独立运行包”，选择目标架构和部署网络后点击“检查安装包”。检查展示资产、资源及知识缺口，不显示凭据值。同架构仅缺标准镜像/Docker 资源时可“准备并生成安装包”；缺业务依赖或另一架构资源时先按下节准备，再重新检查。

已接受的任务在关闭弹窗后继续运行；重新打开同一 Agent/版本可恢复本次状态。请求回执暂时丢失时使用“重新确认本次导出”恢复同一次请求；取消、中断或失败不会提供半成品下载，也不会自动重放写操作。完成后下载安装包。

页面导出默认投影当前推理模型配置、所选业务的 MCP 连接与凭据，以及其工作区 `.env` 和声明环境变量。CLI 默认收集相同业务范围的 MCP 与工作区环境，但不读取在线平台的完整模型投影；自定义模型连接可通过 `--seed-file <本地忽略的*.llm-api-key>` 携带，或安装后重新配置。种子使用 [AgentSeed](../../platform/deploy/agent/types.mts) 的连接结构，属于含凭据的完整配置输入，不将值写进命令行参数。

包内初始连接写入 `config-seed/standalone.json`，环境凭据写入 `config-seed/environment.llm-api-key`，两者权限为 0600；服务器生成的归档同样为 0600，下载副本的权限由浏览器所在系统决定。manifest 只记录来源、摘要和敏感路径，不记录凭据值。归档、原始种子、访问入口和运行备份均需按敏感制品保管，LLM Key 不得提交到远端 Git。

### CLI 与目标架构资源

CLI 使用当前开发环境的工具链；先用实际 Agent/Experiment 替换示例身份：

```bash
./platform/dsh-deploy agent-preview \
  --agent-id my-agent --source experiment:EXP-my-agent-001 \
  --arch amd64 --mode offline

./platform/dsh-deploy agent-prepare \
  --agent-id my-agent --source experiment:EXP-my-agent-001 \
  --arch amd64 --mode offline

./platform/dsh-deploy agent-pack \
  --agent-id my-agent --source experiment:EXP-my-agent-001 \
  --arch amd64 --mode offline --out dist \
  --expected-candidate-sha256 <重新预览返回的candidateSha256>
```

`agent-preview` 只读、不联网，JSON 中的 `resourceReady` 和 `issues` 表示是否存在缺口，命令成功返回不表示已经可以出包。`agent-prepare` 在在线准备机导出已有的匹配标准镜像，下载对应架构的官方 Docker/Compose，并收集所选业务已准备的依赖；不会重建标准镜像或停用已有实例。`agent-pack` 使用已准备的资源，输出 `.tar.gz` 与包外 `.sha256`；进度写 stderr，结果 JSON 写 stdout，可用 Ctrl+C 取消。CLI 不自动补做 `agent-prepare`。

资源默认保存在程序根的 `.local/deploy-assets/<arch>/`，三条命令可用 `--resources-dir` 指定其他资源目录，并用 `--data-root` 选择数据工作区。默认输出目录为数据根 `.local/artifacts/agent-deployments/`；页面任务在其独立任务目录保存状态和归档。

AMD64 与 ARM64 分别准备、分别出包，标准镜像 ID、构建指纹和架构必须匹配。ARM64 可在对应架构在线准备机运行同样命令（`--arch arm64`），再把完整 `.local/deploy-assets/arm64/` 复制到当前平台程序根的同名目录。也可导入已有资源：

```bash
./platform/dsh-deploy agent-prepare \
  --agent-id my-agent --source experiment:EXP-my-agent-001 \
  --arch arm64 --mode offline \
  --image-archive <ARM64标准镜像tar> \
  --docker-assets <包含docker-版本.tgz和docker-compose的ARM64目录>
```

导入镜像和 Docker 文件不等于业务依赖已齐。Node 子包需按该 Candidate 的依赖声明与锁文件准备目标架构 `node_modules`，默认从本机同架构的业务子包收集；另一架构使用完整已准备缓存。Python 的 `requirements*.txt`、`pyproject.toml` 也纳入检查：已有纯 Python `vendor/site-packages`/`site-packages` 可收集并配置容器内 `PYTHONPATH`；原生扩展只复用与目标镜像兼容的已准备资源。缺库、声明无法解析、缓存锁摘要变化或原生库架构不符时停止，不按零依赖出包。当前准备器不代用户创建任意 Python/模型推理环境，不复制宿主 Python、venv、glibc，也不在目标机联网安装依赖或执行安装 Hook。

### 包结构与安装

```text
<独立包解包目录>/
  install.sh
  agent
  manifest.json
  SHA256SUMS
  assets/
    harness.yaml
    workspace/               # 所选业务工作区与知识
    presets/
    managed/                 # 原始业务插件、代码和声明依赖
  runtime/                   # 独立入口、Web、必要的适配与业务实现制品
  config-seed/               # 初始模型/MCP/环境配置，敏感
  images/dsh-runtime.tar
  offline/docker/
```

`.tar.gz` 直接包含上述文件，解压时先创建独立目录。安装器先检查目标架构与 `SHA256SUMS`，核对端口和空安装目录，再复制文件、导入镜像并核对镜像 ID/架构/指纹，最后启动并等待 DSH 就绪。默认安装到当前用户 `~/.local/share/standalone-agents/<agent-id>`；默认在 18500–28999 中选择空闲端口，同时检查宿主监听与 Docker 端口映射。可显式指定地址与端口：

```bash
mkdir my-agent-package
tar -xzf <独立包.tar.gz> -C my-agent-package
cd my-agent-package
sha256sum -c SHA256SUMS
./install.sh --prefix <空安装目录> --host <目标IPv4或主机名> --port 18500
```

未指定 `--host` 时尝试从本机路由/网卡计算访问地址；多网卡、跨主机访问或代理环境应显式提供实际地址。安装器不覆盖非空部署目录；镜像或启动阶段失败会保留安装结果并说明原因，排查后使用该目录的 `agent` 入口继续，不重新覆盖已有状态。Docker 离线引导适用范围见本节的主机要求；宿主防火墙和外部网络可达性仍需现场核对。

### 使用、重配与备份

安装后在安装目录执行：

```bash
./agent status
./agent open
./agent logs
./agent logs -f
./agent stop
./agent start
./agent restart
./agent configure
./agent configure --config-file <受保护的连接JSON文件>
```

`open` 使用本地生成的受保护入口 `state/home/standalone/open.html`，有桌面环境时尝试打开浏览器；服务器上按输出路径安全取得入口，勿把其中凭据写到普通日志。`configure` 默认交互修改已识别模型和现有 MCP 的地址、模型名称与凭据，新增模型仍可使用原生 DSH 设置页面；JSON 模式只接受模型、MCP 与环境字段，不能改写 Agent/版本身份或冻结资产。保存后在当前任务结束时运行 `./agent restart` 生效。原生模型设置、连接配置和新会话均保存在安装目录 `state/`，普通重启保留。

启动器当前没有 `verify`、`backup` 子命令。安装器的 SHA-256 和镜像身份检查证明包与镜像一致；`status`/`logs` 用于查看运行状态，实际访问原生界面并完成目标模型和 MCP 参与的业务任务才验证相应使用路径。完整平台的 `dsh-deploy verify` 不用于独立包。

需要备份时，先确认没有在途任务并停止本部署，在包外安全目录保存 `state/`，再重新启动；同时保留原始独立安装包与其摘要，运行状态不回写 Candidate。例如：

```bash
./agent stop
umask 077
tar -czf <包外备份目录>/agent-state.tar.gz state
./agent start
```

备份包含会话、连接凭据和原生设置，按敏感制品处理。恢复到其他主机须使用对应架构的原始业务包，并另行核对地址、权限、外部服务和实际任务；本命令示例不表示跨机恢复已验收。ARM64 独立包的目标机实测由使用者后续完成，不引用下文完整平台的 ARM64 历史记录作为独立包验收。

## 完整平台安装包

### 当前实现（2026-10-25）

开发与安装环境均使用 `platform/dsh-platform` 的 `prepare`、`start`、`stop`、`restart`、`status`。`start` 默认后台运行，调试使用 `--foreground`；`bin/hep-start` 仅转发 `start`。双架构现场验证结果只在[项目验收矩阵 PA-13](../ai-agent-harness项目验收矩阵.md#pa-13-离线一键打包与安装部署)维护。

### 范围和前置

| 项 | 约定 |
|---|---|
| 打包机 | 在线；可构建镜像、获取 Node/pnpm/DSH 资源和依赖。支持在在线工作机准备目标架构资源。 |
| 目标机 | 离线安装，按目标架构和发行版验证。需要 Docker Engine、bash、tar、gzip；不需要预装 Node、Python、DSH 或 Git。 |
| 架构 | AMD64 包与 ARM64 包分别生成、分别安装；安装器拒绝架构不匹配。 |
| Docker | 安装器要求 Docker 已启动；root + systemd 的 Linux 目标机可先使用下述离线引导脚本，不通过包管理器联网安装。 |
| 数据根 | 必须是含 `AGENTS.md`、`.agents/skills`、`agents/`、`evolution/`、`config/`、`workspace.json` 的真实工作区；安装器默认拒绝夹具，仅测试可 `--allow-fixture-data`。包内只保留原生用户设置 `profiles/harness-platform/cordis.patch.yml`，排除其余平台 HOME、实例登记和 npm 缓存等运行态；设置和凭据按敏感制品处理。 |
| 网络 | 安装过程不执行 `pnpm install`、不 `git clone`、不访问 npm 或 Docker Hub；镜像由本机 `docker load`。 |

207 的现有 AI SOC 容器、镜像和系统配置不停止、不删除、不修改；验证只使用 `/home/aisoc/hep-arm64-poc/` 等隔离目录和空闲端口，不使用 sudo。SSH 只使用用户已确认的免密访问；登录密码不写入仓库、日志或本文件。

### 包结构

```text
harness-engineering-platform-<version>-<commit12>-<arch>/
  install.sh
  manifest.json
  program/                 # 程序仓库 HEAD 的完整已提交快照
    platform/plugin/node_modules/
    runtime/adapters/dsh-web/node_modules/
  offline/
    node/                  # 目标架构 Node 24 tarball
    pnpm/                  # 与锁文件一致的 pnpm
    python/                # 必带便携 Python >=3.10、标准库、PyYAML 和动态库
    dsh/                   # DSH 离线安装树（构建后放入）
    git/                   # Git 客户端及依赖库/离线包（必带）
    docker/                # 可选发行版离线包
  images/
    dsh-<tag>.tar          # docker save 产物
  repositories/            # program.bundle、data.bundle，保留 HEAD 完整历史和 origin
  data/                    # 数据仓库 HEAD + 业务插件依赖 + 专用凭据 + 原生用户设置，敏感
```

`manifest.json` 版本 1，记录包版本、Git 提交和 dirty、架构、源 `$HOME`/程序根/数据根、全部文件类型/权限/SHA-256、运行时组件版本、Git 来源、镜像 tag/Image ID/构建指纹/架构，以及敏感路径。包外生成 `.sha256`。

### Git 客户端

- 安装包必须包含 Git 客户端；不允许只依赖目标机系统 Git。
- 优先使用静态 Git 单文件；否则收集与目标发行版兼容的 Git 二进制、`/usr/lib/git-core`、`/usr/share/git-core` 和 `ldd` 依赖库，写成带 `LD_LIBRARY_PATH`/`GIT_EXEC_PATH` 的包装脚本。动态 Git 使用目标系统的 glibc 和加载器；收集器排除 glibc 库与加载器，打包器拒绝夹带这些文件的旧资源，避免通过 `LD_LIBRARY_PATH` 混用准备机 glibc 与目标机加载器。
- 动态 Git 及其依赖所需的 glibc 版本不能高于目标系统提供的版本；使用较老的兼容构建环境准备资源，并在目标机验证。同架构打包时必须成功执行包内 `git --version`；跨架构只检查资源结构，执行验证由目标机安装阶段完成。
- 安装器把 Git 放到 `<prefix>/runtime/git` 并前置 PATH；包内 Git 不可执行时明确失败，不回退系统 Git。
- 不为 Git 单独制作 Docker 镜像；Git 是宿主短命令，容器化会引入 cwd、uid/gid、凭据和包装成本。

### 打包

在线准备机先准备离线资源目录：

```text
assets/
  node/       # 目标架构 Node 24 tarball
  pnpm/       # pnpm 11.28.5
  git/        # 目标架构 Git；原生打包缺省时可从本机收集
  python/     # 必带便携 Python 运行树或 tar.gz，包含 site/yaml
  dsh/        # DSH 构建产物，构建镜像后放入
  knowledge/  # 可选：已按索引归档的管理知识，含 index.json 与来源文件
  image/      # 镜像 tar（或使用 --image-tag 从 Docker 导出）
  program/platform/plugin/node_modules/        # 目标架构依赖
  program/runtime/adapters/dsh-web/node_modules/
  data/evolution/experiments/<id>/candidate/dsh/managed/<plugin>/node_modules/
```

带运行依赖的业务插件须按其已提交的锁文件，在目标架构准备 `node_modules`，放入 `assets/data/` 下同一相对路径。打包器按已提交来源清单核对并装入；缺少依赖时拒绝出包。原生模块不能直接复用其他架构的开发机依赖。

完整平台包按所选数据 HEAD 的管理指令与技能收集必需知识。资源目录的 `knowledge/` 可提供已有归档索引与原件；打包时逐件核对摘要，只复用本次所需来源，不把缓存正文或无关文件扩充为新的依赖。缓存损坏或必需来源仍无法取得时停止出包，目标机不补取公网资料。

Git 与便携 Python 使用目标系统的 glibc 和动态加载器，资源中不得夹带准备机的 glibc 家族库；Python 的运行树与 tar.gz 均在打包时检查，安装时再次检查解压后的运行树。其余动态库按实际依赖提供，并在目标系统执行验证。工具版本检查失败保留具体命令、退出码及错误原因。

生成安装包：

```bash
./platform/dsh-deploy pack \
  --out dist \
  --assets-dir <离线资源目录> \
  --data-root <完整数据根> \
  --image-archive <镜像 tar>
```

默认从本机 Docker 导出当前架构的标准镜像；`--image-tag` 可显式指定同一标准标签；`--no-image`/`--no-data` 只用于测试或程序包场景。当前数据工作区的六个业务智能体按架构共用一张由锁定 DSH 来源与镜像构建输入确定的标准 Runtime 镜像；无需为各智能体版本分别打包镜像。打包器按所选架构计算标准标签与构建指纹，并核对归档中的标签、镜像 ID、架构和指纹，不接受 POC 镜像代替。`--data-root` 必须是真实工作区；`--allow-fixture-data` 仅用于夹具测试，真实部署不得使用。打包器默认拒绝 dirty 工作树；`--allow-dirty` 仍只打包 HEAD，manifest 记录 dirty，不带入未提交改动。数据仓库也只打包 HEAD；专用 `.local/credentials/` 与原生用户设置 `.local/platform-home/profiles/harness-platform/cordis.patch.yml` 从现场覆盖，保留模型提供方等原生配置；LLM Key 应先放入忽略的 `*.llm-api-key` 专用文件。不复制其余 HOME、Session、缓存或实例登记。两个 Git bundle 在安装时恢复为可操作的仓库，保留来源提交、完整历史及无凭据 origin；路径映射保留为工作树差异，不改写历史。Git 快照和构建产物保持容器非 root 用户可读的权限，不受打包用户的严格 `umask` 影响；归档与凭据仍保留私有权限。镜像构建、依赖安装和数据根一致性检查属于打包机操作，不进入目标机安装过程。

### 安装

目标机没有 Docker 时，可使用 [`bootstrap-docker.sh`](../../platform/deploy/bootstrap-docker.sh)。准备一个目录，放入适配目标架构的官方 Docker 静态发行包 `docker-*.tgz` 和可执行的 Compose 二进制 `docker-compose`，然后以 root 执行：

```bash
bash <程序目录>/platform/deploy/bootstrap-docker.sh <Docker 离线资源目录>
```

该脚本面向 systemd Linux：写入系统前实际执行 Docker、dockerd 和 Compose 以检查兼容性，安装到 `/usr/local/bin` 及 Docker CLI 插件目录，创建并启用 Docker 服务。已有 Docker 时复用现有安装；命令缺失但已有服务配置时停止，不覆盖残留配置。主机仍须具备 Docker 所需的内核和系统工具；其他系统先按对应方式安装 Docker。平台安装包也可由外层部署脚本携带并调用该引导脚本。

```bash
tar xf harness-engineering-platform-<...>.tar.gz
cd harness-engineering-platform-<...>
./install.sh --host <目标IPv4> --port 18120 --start
```

NAT 或反向代理部署增加 `--public-url https://<公开域名>/hep/`，`--host` 仍填写目标机实际拥有的 IPv4。公开入口同时用于浏览器链接和 DSH 原生 Host 校验；本地监听用于就绪检查，公开 URL 不作为可绑定网卡地址。业务网关的公开来源仍须按实际端口或代理路由核对。

安装和 `verify` 的默认程序目录为当前用户的 `~/work/harness-engineering-platform-data`，默认独立数据根为 `~/harness-engineering-platform-data`。两者均相对执行用户的 HOME 展开；可通过 `--prefix` 和 `--data-root` 显式覆盖。

流程：校验 manifest、架构、全部文件 SHA-256、标准镜像身份和目标目录；校验数据根是真实工作区（夹具默认拒绝）；恢复程序/数据根；按源 `$HOME` → 目标 `$HOME` 重写实例登记、Compose、`workspace.json`、`business-access.json` 等已知文件；指定 `--host` 时，将业务网关监听地址、公开来源和管理入口改为目标地址与平台端口，并可用 `--gateway-port` 指定并行部署所需的空闲网关端口；安装并执行校验 Node 24/pnpm/DSH/Git/Python+PyYAML；`docker load` 并核对导入镜像的 ID、架构和指纹；运行 `platform/dsh-platform prepare --offline`。包含镜像的安装包在 Docker 不可用时明确失败。`--dry-run` 只校验和展示计划；`--skip-image` 显式跳过镜像导入；`--strict-paths` 在仍有旧路径时失败。

安装的程序目录和数据根必须独立且不存在或为空；失败只清理本次新建内容。镜像导入在包内工具验证之后执行；Docker 中共享镜像不回滚。`--start` 调用统一后台启动入口；启动失败保留安装结果、日志和重试路径。指定 `--host` 时，启动前检查活动的 firewalld 或 UFW，放行管理端口和启用的业务网关端口；firewalld 按监听地址对应网卡的区域分别补齐即时与持久规则，网卡未分配区域时使用默认区域，不执行 reload。防火墙修改失败保留安装目录并明确提示管理员处理；未检测到这两种防火墙不代表客户端可达，仍须从客户端核对。

新建数据工作区未显式提供账号时，使用初始化模块的默认账号；初始化页预填同一来源并允许修改，已有账号不覆盖。账号只写入数据根 `.local/credentials/admin.json`，权限为 0600。完整数据快照安装继续保留其账号配置。`verify` 按 DSH 原生工作区登记核对唯一数据根，不依赖仅原生首次使用流程写入的可选默认标记。

本地目录复制、归档压缩与解包、Docker 镜像导入导出不套用短命令的固定十分钟上限，避免大安装树在较慢磁盘上被误中断；失败仍按命令退出码报告，完成后仍执行摘要或镜像身份核对。打包进度写入标准错误，标准输出继续返回结果 JSON。

不自动启动业务实例。安装回执列出待重建实例；旧平台 Session 和 Docker 命名卷不自动迁移。跨主机安装时显式传入 `--host`；并行部署另传 `--port` 和 `--gateway-port`。完整数据根包含平台密码和 LLM API Key，归档仅允许打包用户读取，分发和存放须按敏感制品管理。

### 部署验收命令

安装后运行：

```bash
./platform/dsh-deploy verify --prefix <安装目录> --data-root <数据根> --url http://<host>:18120/hep/
```

安装和启动共用业务网关初始化：新工作区默认启用网关，补齐监听地址、默认端口 `53105`、公开来源、登记列表及本地共享密钥；保留已有登记、自定义地址和显式关闭状态。显式关闭的工作区必须先启用网关，才能从 GUI 或管理助手创建业务实例。初始化还修复配置文件和共享密钥的 Runtime 读取权限，即使配置内容没有变化也会执行。

检查程序文件摘要和权限、真实工作区资产、Profile Skill、原生默认工作区、只读启动预检及网关完整配置与密钥。指定 `--url` 时还核对平台与业务网关均由当前受管进程监听，使用专用账号文件登录，调用真实 inventory RPC 比对数据根和 workspace ID；其他 HTTP 200 服务不能通过。未指定 URL 只表示资产和运行环境检查，不表示在线验证。

```bash
cd <安装目录>
./platform/dsh-platform start
./platform/dsh-platform status --json
./platform/dsh-platform restart
./platform/dsh-platform stop
./platform/dsh-platform start --foreground
```

后台启动无需 `nohup`、`setsid` 或预先 source 环境；日志路径随启动回执给出。 已由 systemd 等服务管理器托管的环境，应使用对应服务的启停命令；直接重启其子进程会触发原服务的退出清理，可能停止刚启动的平台。配置变更优先使用原生重载，并核对实际监听；新增监听未随重载启动时，在会话空闲后通过原服务重启。
