# 07｜关键 POC、验收基准、ADR 与风险

## 1. 验证范围与状态

下列条目定义 POC 方法，结果以实际证据为准；不能把历史候选的整体状态从设计推断为已通过。Session/feedback/cancel API、跨容器 Trace 持久 ACK、业务发布和组合 Gateway 须按锁定 DSH 版本实测。新增业务运行 POC 仍未执行，阶段条件引用 [05](05_实施路线与迭代计划.md)。

| T16 Profile/种子装载 | 检查目标 Profile/Preset/bundle 与覆盖，分别恢复新卷和新 Session | 声明、实际 profile、Candidate 种子与行为可核对，开发身份未被替换 | 修真实装载路径，不以保存配置证明生效 | 选定相关接入时 |
| T17 双用户 Session/Schedule | 同 Agent 共享 Runtime 下两个非 owner 用户从 UI/Remote 交叉操作，检查模型工具、到期投递和重启 | `04` 所列全部已开放入口服务端归属一致，不能越权或串投递 | 未覆盖入口保持关闭，记录原生接缝缺口，不提升为 owner | 即时任务所选路径的实施结果见 [21](21_统一网关与MCP控制实施验收.md)，Schedule 仍未覆盖 |
| T18 业务网关与入口一致性 | 双判断、HTTP／WS、附件、下载、路由前缀及容器直连测试 | 相同用户身份与来源绑定，已撤销用户不能重连，绕过公开入口不能访问 | 收窄开放路径，解决真实传输与网络接缝 | 所选 HTTP／WS 与下载路径的实施结果见 [21](21_统一网关与MCP控制实施验收.md) |
| T19 MCP 动态收紧 | 两会话、进行中的组合、资源读取、排队和重试；断网后恢复 | A 的受限子操作未到上游，B 正常，在线目标取得版本回执，重连不恢复旧许可 | 未确认目标暂停受保护动作，不能仅刷新目录 | 相同可信上下文之后 |
| T20 信任与护栏联合闭环 | 固定版本接入身份提供方、原子及组合调用、必要确认和一种报告通道，再测第二业务 | 正常结果可交付，信任失效和越权实际被阻断，输出前检查及目标侧证据可关联 | Mock 与真实接入分别报告，不把局部机制写为全部覆盖 | 网关与调用执行点之后 |

每条 POC 的结果可以是 **pass / fail / inconclusive / not-run**；必须写出证据路径、锁定镜像/依赖、运行环境、失败/未知，不能因“架构图通过审阅”标成 pass。

### 2.1 T12：业务组合的最小验证与复用候选

业务设计引用 [W6](04_核心业务闭环与服务接口.md#mcp-business-composition)，阶段顺序引用 [05](05_实施路线与迭代计划.md#mcp-composition-route)。先选实际只读两步任务，例如查询资产后用资产 ID 查询告警，保存真实输入、第一步输出、第二步实际参数、最终业务结果和子调用证据；验证已有凭据与登录缓存复用、结果范围、工具 Schema，以及外部 DSH 的初始化、发现和调用。页面交互在 UI-04 验收，T12 不要求先建界面。

异常验证覆盖无效输入、缺少前置输出、授权失败、下游超时和前置步骤失败后的依赖停止。涉及写操作时，另用可控操作验证超时结果未知与对账，不能自动重跑整个组合；只读 POC 不能证明写操作恢复已成立。页面测试和工具调用必须使用同一执行入口，不另做仅供演示的测试逻辑。

以相同 Case、模型、输入和已核验上游状态比较“原子工具逐个调用”与“单组合 Tool”，遵循 [03 的外部状态合同](03_存储架构与数据契约.md#comparison-environment)。记录任务正确性、模型往返次数、token、总耗时及下游调用次数；减少模型调用不等于减少业务 API 调用。收益未证实时保留观察与限制，不宣称已提高准确率或效率。

下列开源能力是待 POC 验证的复用候选，未选型或安装。来源核对日期为 2026-10-12：

| 候选 | 拟复用范围 | 需要验证的边界 |
|---|---|---|
| [OpenAPI Arazzo](https://spec.openapis.org/arazzo/latest.html) | API 调用序列、依赖、输入/输出和成功条件的标准定义 | 当前最新规范为 1.1.0；候选组件只确认支持到 1.0.1，POC 先验证共同支持的 1.0.1 范围；不自行设计通用编排格式 |
| [Redocly Respect](https://redocly.com/docs/respect/commands/respect) | 执行 API 序列的命令行验证与测试证据 | 文档支持 Arazzo 1.0.1；CLI 测试能力不等于可直接嵌入平台执行内核，需实测授权、超时和结果映射 |
| [@jentic/arazzo-ui](https://github.com/jentic/jentic-arazzo-tools/blob/main/packages/jentic-arazzo-ui/README.md) | React 只读流程图和定义说明 | 文档支持 Arazzo 1.0.0/1.0.1；验证与当前界面依赖兼容、能否关联实际步骤状态，不据此引入编辑器 |

执行器以这个固定两步 POC 决定：优先验证现有实现能否复用授权/缓存、参数映射、超时、依赖停止和有界业务输出，并供页面测试与 MCP 调用共用。集成成本高于当前任务时，用最小 TypeScript 固定组合复用现有调用逻辑，不建设通用 Arazzo 引擎。[Jentic TypeScript runner](https://github.com/jentic/jentic-arazzo-tools/blob/main/packages/jentic-arazzo-runner/README.md)目前仍在积极开发且未发布 npm，不作为默认依赖。Arazzo 的 API 描述不能直接证明原生 MCP 步骤可用；MCP 步骤经已有 MCP 客户端执行，并单独验证协议与结果映射。

### 2.2 业务运行 POC 的具体接缝

**原生授权接入。** 在 rc.2 创建真实非 owner Peer，对 Session、Workspace 和事件订阅分别验权；验证 `registerPolicy`、同步 `bindings/conditions` 与 `invalidate` 的实际行为。标准浏览器 owner 身份不能代替业务认证。原生交互参与目前是 owner-only，因此必要确认必须另验明确受控接入；无法覆盖时保持该动作未开放，不能传递 owner。Exact Fetch、插件自注册 HTTP、任务 API、附件和产物各验证自己的授权路径。

**读取与执行旁路。** A、B 在同 Agent 建立不同文件、任务与报告，通过 UI、Remote、工具、路径参数和下载链接交叉操作；包含文件读取、目录遍历、Shell、代码变体、插件 HTTP 和组合直调。原生文件沙箱的写入约束不能当作读取隔离。通用能力未能约束时关闭并明确能力缺口，测试须保留真实内部调用，只在外部服务边界使用受控替身。

**网关传输与网络。** 优先用 `httpxy` 原型验证 DSH 原生 Request／Response 和 WS Upgrade 的对接，测试 SSE、流量取消、慢响应、资源路径、Cookie、Host／Origin、重连和撤权时已建立连接。未确认前不把 HTTP 转发成功等同于 DSH 双向会话兼容。业务容器私有网络切换核对现有本机依赖，测试原公开端口不能绕过。

**风险时效与恢复。** 对同进程和跨实例分别记录限制提交、应用、回执及下一实际派发的时间；验证 [W9](04_核心业务闭环与服务接口.md#dynamic-mcp-control) 的首期传播目标，未达标保留实测并修正方案。覆盖旧版本迟到、快照缺失、过期、插件卸载和信任撤销。每个拒绝还核对上游未收到该操作；已收到的写请求取消只记录实际观察，不能补写回滚成功。

**身份与输出。** 采用无害合成风险和敏感标记，检查确认绑定实际主体、工具、参数、目标和版本，确认后重新授权；对选定非流式报告在发布前检查接收方与内容，正常报告摘要不变。真实身份登记、核验及撤销需要真实提供方回执，外部服务未就绪时此项保持待验收。更换提供方或检测组件做薄适配回归，不要求修改外部项目源码。

以上 POC 的通过条件是实际行为，不是插件接口可解析或架构图已绘制。开发规范见 [20](20_业务访问与运行控制插件开发规范.md)。

## 5. 失败场景与恢复矩阵

| 故障 | 权威事实还在哪里 | 正确行为 | 不正确行为 |
|---|---|---|---|
| Candidate 修改中断 | Git 工作树/已冻结摘要 | 按 diff 找到剩余修改；人工确认后继续 | 复制一份“最新 Candidate”到 PG 继续编辑 |
| 评测被中断 | 已产生的 Run/原生 Session | 保留完成/失败/未运行项和来源，必要时新 Run 重测 | 用新结果覆盖旧 Run |
| 容器创建成功但客户端超时 | Docker 实际状态，外部操作记录可能未知 | 以精确 owner/容器/来源核对，不能确认 unknown | 直接再建同名容器 |
| DSH Session 存在但 UI 丢链接 | DSH 原生日志 | 从 owner+Runtime+Session 恢复只读历史 | 生成一个新空会话掩盖丢失 |
| Meta 工具重复调用 | Operation 唯一 request_key（如已引入） | 同一回执与状态对账 | 将相同修改执行两次 |
| 下游 MCP 写操作执行结果不明 | Server 回执/可查询业务状态 | unknown，人工或安全对账 | 同参数自动补发高副作用工具 |
| PG 不可用（如已引入） | 已提交状态是否成功需要 DB 重试查询 | 停止受控修改，恢复后按 operation ID 核查 | 写本地可编辑影子 DB 补账 |
| DSH 原生 Query 缺事件 | 原始可读取部分与可靠覆盖范围 | 标注缺口、研究 Schema/最小探针 | UI 虚构父子 Span/完整 Trace |
| 撤回已发布版本 | 不可变资产/Session 历史 | 停止新派生/新会话路由，保留旧引用 | 删除旧版本资产和历史会话 |

## 6. 工程质量标准

- 当前工具：稳定输入/输出、错误码、来源摘要、最小重跑示例、少量合同测试与真实任务验收。
- R2 以后：ID 唯一作用域、恢复/删除语义、来源不可变证明、状态时戳、备份复原。
- R3：每个跨工具步骤有真实来源，失败能定位，避免重复 Candidate/Case 写者。
- R4：修改型动作都可预览/确认/幂等/对账；Meta 没有自由 Docker/SQL 凭据；来源变化拒绝旧确认。
- R5：只有产品真实多人/长驻/第三方工具暴露时再实施所需服务端认证/访问隔离/持久采集与运维流程。

## 7. 风险与应对

| 风险 | 早期可观察信号 | 最小措施 |
|---|---|---|
| DSH 预览版 API/Session 变化 | 升级后 Session Query/模型选择/事件 schema 失败 | 镜像/依赖锁定 + 独立兼容测试 |
| 评测证据不可靠 | 相同 Case 反复结果差异无法解释 | 固定来源/评审器/资源条件，保留样本数与不可比 |
| 工具链过度抽象 | 一人用却出现多个服务/双模式 | 删除未被调用的层，保留现有 CLI |
| Git 与 PG 双写 | 同一 Candidate/Case 可在两处修改 | 单次迁移写权，旧入口只读或委托 |
| Trace 过度承诺 | Session 中断后 UI 仍显示“完整” | 显示覆盖/未知，TR02 另立验收范围 |
| 多变体伪等效 | 只比较平均分，关键 Case 大退步 | 事前业务质量下限+退化红线+资源证据 |
| LUI 结果缺少操作证据 | 答复“完成”但没有操作回执 | 共用 Service/真实 ID/证据链 |
| MCP 展示与执行脱节 | 页面测试成功，外部 tools/call 失败；图中状态与实际步骤不符 | 一份定义、同一执行入口、真实子调用与外部 DSH 验证 |
| 多用户共享 Runtime 串数据 | 猜 ID、文件读取或插件 HTTP 可以访问他人资源 | 开放前做服务端归属与旁路验证，未覆盖能力保持关闭 |

## 8. 记录所选故事的决策

引用原始证据，记录故事范围、实际镜像/依赖、需要的 POC 及结果、恢复路径、收益、复杂度、限制与下一步。未选变体/Meta/MCP 不增加对应门槛；阶段条件只在 `05` 定义。已有 Experiment 或任务记录足够时直接引用，不要求创建阶段审批单或追踪数据库。
