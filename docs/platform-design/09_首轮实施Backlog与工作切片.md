# 09｜首轮工作切片建议

> W01–W20 是候选工作切片。执行前核实现有实现、工作树与来源锁，按实际需求选择一条链路；当前能力与证据见项目验收矩阵。

## 1. 开工顺序（推荐按一个纵向用户故事走通）

**首选故事**：“真实案例失败 → 定位原因 → 修改 Candidate → 同口径 dsh-eval → 比较 Run → 人工 Decision → 再运行得到同样的可核查结论。”

先完成选定研究路径。有重复操作痛点即可工具化；变体只在资源/组件变化属于研究假设时选择，三条故事不是必须逐条完成的顺序。阶段条件见 [05](05_实施路线与迭代计划.md)。

比较环境统一引用 [03](03_存储架构与数据契约.md#comparison-environment)，任务完整依赖引用 [08](08_112项任务追溯矩阵.md)。下表是工作建议，不表示已经执行。

## 3. 第一个两周迭代的更精确安排

- **Day 1**：明确 1 个研究问题、1 个 Case/预期、固定有效 Baseline（首个实验可为 `none:first-experiment`）、真正可调用的模型/工具，检查仓库工作树和现有验收矩阵。提交研究假设前不创建平台表。
- **Day 2–4**：完成 W02/W03，获得可核对的真实 Session/Run。若 API/凭据/只读挂载失败，只修阻断点，不开启新 Web 项目。
- **Day 5**：做 W04，确认改善/退化/证据不足和下次工作，不自动发布。
- **Day 6–8**：回放首个研究结论，核查反例、外部状态和恢复。只有选择了变体假设时才执行 W05/W06；否则直接观察工具化痛点。
- **Day 9**：按已得到的重复操作频率排序工具痛点（W07），给最重要的一个写小用户故事。
- **Day 10**：依据证据决定是否进入 R1；没有已证明价值则继续 R0。所有日期均可顺延，不跨越来源/评测真实性门槛。

## 4. 工作切片的选择依据

1. 这次修改解决哪一个当前真的出现的问题？
2. 能否复用现有 `workspace-management`、`source_contract.py`、`dsh-dev`、`dsh-eval`、`evaluation.md` 和 Run？
3. 哪个文件/服务拥有当前唯一可编辑事实？是否出现了第二个编辑入口？
4. 能用一个真实 Case/Session/Run 验证，而不是只验证 HTTP 200 或静态类型吗？
5. 若本轮工具化无收益，新增代码能否轻易撤回？

每次选择一条当前链路和最小可验证切片。

## 6. 已选第一阶段：四目录并行计划

本轮已明确选择首页、智能体研究管理、实例管理和 MCP 工具组合作为自用工具切片。四个目录是独立 Git checkout，按下表使用分支；它们不是共享 `.git` 的 Git worktree。平台切片按项目路径验证，复用现有 CLI 和研究资产，不增加数据库、租户或发布审批；业务 Harness 语义变化另按研究流程处理。

| 目录与分支 | 任务及修改范围 | 完成标志与验收路径 |
| --- | --- | --- |
| `ai-agent-harness` / `feat/platform-stage1-foundation` | 公共 RPC 合同、Host 分流、四页导航、首页及正确名称的 Logo；维护构建、原生认证集成、文档与最终验证。 | 三个模块通过同一认证通道接入，首页数据与真实索引一致；认证、卸载、构建与浏览器证据可核查。`PA-12`。 |
| `ai-agent-harness-copy1` / `feat/platform-stage1-agents` | `src/agents/` 与对应测试；版本创建、继承/融合查看、特性声明与实例观察、Candidate/评估/Decision 编辑、Case 评测与 Run/轨迹查看。 | 固定父来源可恢复；编辑摘要冲突拒绝写入；评测复用原入口；已有 Run 不改写。`PA-03/04/08/10/12`。 |

先将公共合同提交分发给三个目录，随后三个模块可并行实现和测试。各目录只修改自己的功能文件；公共入口、依赖和文档由基础分支维护。基础分支依次合入实例、智能体和 MCP 的功能提交，再进行跨模块认证、浏览器与现有 CLI 回归。功能测试可以并行，集成入口修改和合入必须串行。

自动化通过、真实 Docker 生命周期、受控原生认证/浏览器、完整全局 DSH 启动及外部业务验收分别记录。当前完成状态、阻断和后续支持需求只在[项目验收矩阵](../ai-agent-harness项目验收矩阵.md)维护；本节维护任务分工及完成标准。
