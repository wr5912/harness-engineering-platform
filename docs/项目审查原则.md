# 项目审查原则

## 用途与依据

本文件说明本项目怎样审查提交、代码、方案、文档、数据、Harness 配置和研究结果。项目基本约定以根级 [AGENTS.md](../AGENTS.md) 及其指定的项目解释为准；本文件只维护审查范围与方法。

项目 AI 开发工具的 Harness 与目标智能体的 Harness 都是重点审查对象。审查既核对实现正确性，也核对配置设计、实际生效、任务行为和可以删除的复杂度。

审查结论支持平台交付与 Harness 研究判断，分别核对功能合同和研究证据；不表示生产级 Agent 平台已经完备，也不为每个 Experiment 增加固定检查清单。

## 范围与深度

开始审查时，先确定用户目标和允许得出的结论，记录所依据的提交及工作树状态。当前状态以实际配置、文件和运行环境为准；历史报告和 Memory 只能提供线索。

收到明确审查请求时，默认审查当前工作树中的全部可维护项目资产，包括代码、测试、配置、技能、Harness、当前需求、测试数据与评估口径、文档及其接口关系；提交差异只是线索，不能代替对未改动部分的审查。按职责逐项核对实际内容，再沿关键调用链检查入口、生成器、消费者和同类路径。

只有用户明确限定对象时才改为专项审查，结论必须标明该限定范围。普通修改任务完成前的自检仍按改动影响进行，不因此变成全项目审查。精准修改限制的是修改范围，不是理解范围。

审查深度按平台功能与研究结论的实际影响分配，但全量审查不能只列资产清单而不检查内容；重要调用链应深入核对。未检查的当前资产必须说明及其对结论的影响，不能声称已经完成全项目审查。不涉及的能力不自动成为缺陷，也不要求为了全量审查对所有运行路径重新做实机验收。

Run 和日志是执行证据；`evolution/history/imports/` 保存外部迁移来源与处置记录，不是运行产生的数据。全量审查不要求逐条扫描全部历史记录；审查具体研究结论、回归、故障或来源可信度时，应沿主张核对相关原始材料与生成路径。

## AI 开发工具的 Harness

开发工具 Harness 包括实际组织 AI 开发工作的指令、技能、模型与工具配置、上下文和执行约定。审查时重点判断：

- 项目原则、局部指令、技能和任务提示是否一致，触发范围是否准确，是否存在重复或相互冲突的要求；
- 模型、推理配置、工具、任务拆分、重试和停止条件是否满足当前任务，复杂配置是否有实际收益；
- 当前目标、有效规则和相关资产是否进入上下文，过时材料和重复说明是否造成干扰；
- AI 是否保持开发身份，选对文件，保存产物，保留人工修改，执行必要验证并准确报告结果。

规则和技能本身也可接受审查。发现冲突时修改共同来源，不追加相反说明让执行者自行取舍。没有测量时，不声称准确率、token 或性能已经改善。

“规则存在”“技能被调用”或“文件可解析”只证明对应局部状态。声称开发质量发生变化时，需要相应的行为观察。

## 目标智能体的 Harness

目标 Harness 包括角色指令、Preset、Skill、Plugin、MCP、模型、上下文和完成条件。审查时重点判断：

- 任务范围、输入、能力、工具、输出和完成条件是否相互匹配；
- 各组件组合后是否仍遵守同一任务合同，工具名称和调用说明是否与实际能力一致；
- 任务怎样开始、取证、调用工具、处理结果和结束，是否存在证据不足时完成、错误结果当作成功、条件丢失或无收益重试；
- 配置变化是否带来与研究目标相关的可观察行为变化，是否同时引入回归；
- Guard、审批、权限和工具限制是否服务当前研究，是否误拦必要行为。

验证规模由研究问题决定。一个成功输出不能证明未覆盖场景；没有改善、假设被否定或证据不足都是有效研究结果。缺少当前不需要的生产级治理能力不列为通用缺陷。

继承或融合审查还须核对来源集合是否覆盖仍需保留的并行能力、文件差异是否已有明确取舍，以及回归测试与实际装载是否指向目标 Candidate。来源版本的测试通过、目标无缺失文件或历史修复提交已在分支中，都不能证明修复已进入当前目标。具体盘点与检查步骤见 [harness-evolution](https://github.com/wr5912/harness-engineering-platform-data/blob/main/.agents/skills/harness-evolution/SKILL.md)。

被测智能体之外，评审、归因等由适配层装载并影响研究结论的 Harness 也在审查范围内。按实际运行角色核对它们的来源、配置、可见材料和输出影响，不因都叫 Preset 就归入业务 Agent，也不因位于适配层就忽略。

## 代码与适配层

代码审查从实际入口追到解析与校验、状态和副作用、失败与恢复、输出及直接消费者，核对边界条件和同类路径。检查测试是否经过真实问题路径及关键失败分支；测试通过不等于已审查实现。兼顾正确性、简洁性、模块边界、相关安全风险和性能，不把未来生产平台的完备性当作当前缺陷。访问安全的当前从宽选择以根级 [AGENTS.md](../AGENTS.md#项目定位与工作方式) 为准，不按生产安全基线列为缺陷；提出收紧建议时说明真实暴露、实际影响与用户要求。

DSH 适配层的启动、来源选择、装载、评测、证据记录和校验应按真实调用关系交叉检查，不能只看单个脚本或 Mock。静态合同、容器装载、真实 Session 与研究效果分别使用相应证据；缺少某层验证时只限制对应结论。

审查跨来源共享的当前事实时，枚举其全部可编辑声明点、生成入口和读取方；例如 DSH 版本应核对全仓锁、已有 Candidate、新建 Candidate 的生成结果及实际镜像身份，确认只有一处可编辑版本声明。

## 配置、实现和资料之间的关系

开发配置与目标资产按根级 `AGENTS.md` 的对象定义区分。启动器、解析器和校验器按其实现职责审查，不因服务于 AI 工作流就全部归类为开发智能体配置。

| 关系 | 判断内容 |
|---|---|
| 开发身份与业务指令 | 开发工具读取业务指令是为了编辑资产，不应无意切换成目标业务 Agent。 |
| 目标选择与实际运行 | Agent、Preset、来源配置和实际装载对象一致，不依赖名称相同推断。 |
| 编辑与产物保存 | 修改进入约定事实源；HOME 中有价值的新资产不被当作缓存丢弃。 |
| 修改与生效 | 源码写入不等于实例已经加载；按[根级变更生效原则](../AGENTS.md#项目定位与工作方式)核对实际装载和任务行为。 |
| 运行与评价 | 被测对象、输入、评审与归因角色、判断口径对应实际运行；结论所依赖的配置来源可追溯，不把环境变化全部归因于被测 Harness。 |
| 记录与后续开发 | 研究记录保存必要依据，但不自动成为需求、验收标准或源码事实源。 |

比较期间保持资产、输入和判断口径稳定；口径变化后重新执行受影响部分。工具选错目标、丢失产物或执行失败却报告成功，不能由操作约定代替修正。

## 文档与数据

文档应直接说明用途、当前能力、过程和结果；命令、路径、配置样例及“已实现”描述要与实际版本一致。数据按字段语义表达，不能把目标当作输出清单、预期行为当作执行证据，或把人工说明当作自动评分器。

同一当前事实只保留一个可编辑来源。生成内容有问题时检查生成逻辑及其消费者，同时保留人工补充和原始证据。改善可读性不得静默改变字段类型、业务范围、阈值或稳定标识符。

用词审查以[项目术语表](项目术语表.md)为依据，先枚举全部出现位置，再按语境检查正文、界面、模板、生成器、解析器、示例与相关测试断言。全仓统一任务包括受控副本和原始导入；命令、路径、协议字段、稳定 ID 及原始执行证据保持其身份，不作机械替换。

审查质量以内容是否准确、可理解和可维护为准，不使用禁词、英文数量、固定篇幅或主观“AI 味”评分。

导入或替换成套文档时，人工核对当前入口与规范适用关系、本地文件/锚点/图片链接、旧入口的直接入站引用，以及跨章节的事实源和条件依赖。完整任务与局部覆盖、设计与实际状态分别检查。原始输入和历史归档的既有非便携链接注明来源限制，不为通过检查改写事实。经用户明确授权形成原位置本地修订版时，区分输入与当前版本，核对原摘要、恢复提交、当前摘要及直接消费者；历史摄取清单仍记录当时事实。复用现有规则和临时检查即可，不由文档治理需求新建评分系统或校验平台。

## 发现与证据

| 类型 | 表述要求 |
|---|---|
| 确认的问题 | 给出位置、触发条件、影响和证据；需要当前修改时说明原因。 |
| 设计建议 | 给出与当前目标相关的依据、取舍和验证方向，不写成已发生故障。 |
| 尚未验证 | 限定已有结论；只有影响当前目标时才要求补充验证。 |
| 当前不需要 | 不列为缺陷或待办，不用生产平台清单衡量本项目。 |

静态证据可以证明确定的指令冲突和配置不匹配；效果改善和行为变化需要对应观察。审查记录应区分源码阅读、真实代码执行、Mock、容器或模型观察以及作者提供的记录，未执行的测试不得报告通过。Run 结论还应核对被测资产、输入、执行器及评审或归因 Harness 的实际来源；缺少可追溯信息时明确限制结论，不从名称或当前文件推定当时内容。

缺陷验证保留会触发问题的真实内部调用，只在必要的外部边界隔离依赖。投入与问题规模相称，不能用整体 Mock 代替核心路径，也不为没有当前使用依据的假想条件建设防御系统。

## 修改建议与结论

修改建议围绕共同根因，覆盖直接相关入口和同类路径，并保持最小完整范围。一条实质性意见应说明位置、触发条件或设计依据、影响、证据、修改方法和适当验证。

报告先说明审查基准、实际覆盖的资产与调用链、未覆盖部分和总体判断，再列出值得当前处理的发现，最后说明验证限制和停止点。仅列出文件名或测试结果不算已经审查其内容；没有重要问题时直接说明，不凑数量，不重复已修问题，不把未覆盖事项包装成新任务。

优先级按当前使用需求、功能行为与研究结论所受影响确定，不强制控制编号、风险打分或生产事件等级。`reject`、`inconclusive` 和未验证分别按其事实含义记录，不等同于提交失败。

用户只要求 review 时，不直接修改或推送仓库；获得实施授权后再按项目规则修改。不得为使当前实现通过而降低目标或抹去证据。

## 维护方式

本文件是审查范围与方法的唯一可编辑维护位置。已有技能或工具需要这些方法时引用本文件，不复制正文。修改本文件时也核对它与项目基本约定、验收矩阵的关系，并用实际审查情形检验能否准确划定范围和结论。历史报告、Memory 和项目验收矩阵各自保留版本观察、辅助线索和验证状态，不替代本文件。

使用普通 Git 工作流维护本文件，不新增规则数据库、快照、审批、Hook、CI 门禁或形式化评分系统。只有共同问题持续影响审查判断时才修改原则，不为单个缺陷增加永久规则。

平台能力扩展时，按实际选择的功能合同确定受审资产和证据；研究流程的适用边界不构成平台功能的永久豁免，未纳入当前需求的后续能力也不自动成为缺陷。
