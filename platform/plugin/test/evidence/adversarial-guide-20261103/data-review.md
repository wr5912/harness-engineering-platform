## 确认问题

### P2：无关损坏批次会阻断健康 Run 的样本列表与健康批次读取

- 位置：`platform/plugin/src/evaluation/datasets.ts:130–132`，以及 `datasets/list` 的436–437行、`response` 的300行；页面直接消费者为 `platform/plugin/src/evaluation/dataset-view.tsx:97–101`。
- 触发：目录内一个符合登记文件名的批次出现坏JSON，用户查看另一健康 Run 的决策样本或直接读取健康批次。
- 根因：`all(root)`先无隔离地读取全部JSON；列表按run_id筛选发生在全量读取之后。健康批次的`response()`为核对跨批次关系也再次调用`all(root)`。一个坏文件的解析异常扩大到所有当前批次任务。
- 实证：`data-repros.mts`调用真实`createDecisionDatasetHandler`，仅在本次自有`.local`夹具中写一个可列出、可读取的旧版健康候选，再加入另一Run的坏JSON。加入前列表1项、健康读取1条；加入后，即使按健康run_id筛选且`include_eligibility:false`，列表仍`invalid_dataset`，直接读取健康批次也失败。回执为`data-repros.json.datasetIsolation`。
- 影响：损坏数据的定位与恢复会妨碍无关健康数据的查看。当前实际91个批次可读取，本次没有观察到现存坏JSON；这是已复现的错误扩散路径，不是声明实际业务资产已经损坏。
- 最小建议：读取目录时保留逐批次读取结果与明确错误，列表和健康记录可读；合格导出需要全局同源关系时，不可静默忽略坏批次，应将“关系核验不完整”作为资格阻塞原因。不得为恢复列表而放宽训练隔离。
- 验收：健康和坏批次并存、按Run筛选、直接读取健康记录均能得到准确对象与坏文件定位；来源关联无法确认时合格导出仍阻断，修复坏文件后恢复核验，其他正常路径保持。

## 设计建议与被排除的候选发现

### 训练文件核验的verified应保持明确层次，不等同KEV数据质量或实际执行证明

`inspectDecisionTraining`当前核验回执声明的Run、文件字节、四分区/组/身份、相同输入交集、执行状态字段和工件绑定。隔离复现说明，即使原生`questions.route.label`不属于候选，文件摘要与回执字段仍可使`verified:true`。但`compute-generation-contract.ts:38`明确说明文件核验不代替实际执行、人员标签、效果或部署，且要求复用已有KEV审计与编码检查，因此不能仅凭上述反例认定它违反现有“数据质量已经通过”的合同。

`questions.*.label`确为既有原生格式：数据侧桥接器`platform_export.py:440–455`从目标映射生成；锁定上游`split_data.py:63–77`检查标签类型与候选。复现中的`_meta.run_id`、`label_status=suggested`则不是所有IR/legacy原生入口的统一必填合同，不拿这些额外字段制造来源缺陷。

建议用户看到verified时明确为“训练材料核验”，需要扩展核验时引用已有数据审计/编码回执与冻结文件摘要；不新造生产化认证、不把语义真值判断强塞进文件校验。相关复现保存在`data-repros.json.trainingSource`，仅作为边界证明及改进建议，不列确认缺陷。
